이 글은 [EC2 Docker 빌드 중 서버가 멈출 때: 메모리 스래싱과 swap](/posts/ec2-docker-build-thrashing)에서 이어진다. 앞 글에서 swap으로 스래싱을 완화했지만, 근본 해결은 빌드를 EC2 밖으로 옮기는 것이었다.
</Callout>

<Callout type="info">
**TL;DR**

EC2에서 하던 Docker 빌드를 **GitHub Actions 러너로 옮기고**, 만든 이미지를 `docker save | gzip | ssh 'docker load'`로 **레지스트리 없이 EC2에 직접 전송**했다. EC2는 이제 이미지를 받아 `compose up`만 한다. 단일 인스턴스에 이미지 버전 관리도 하지 않는 상황이라 ECR은 과설계라고 판단했다. 빌드발 메모리 압박은 사라졌지만, 배포 시간 중앙값은 **4.8분에서 7.2분으로 늘었다.** 늘어난 시간의 대부분은 전송이 아니라 러너의 빌드 시간이었다.

</Callout>

## 왜 옮겼나: swap은 완화책이었다

앞 글에서 swap 4GB를 추가하면서, swap 사용량이 기준치를 넘으면 경고하는 알람도 함께 걸어뒀다. swap은 최후의 완충 장치여야 하니, 평상시에 쓰인다면 메모리가 빠듯하다는 뜻이기 때문이다.

이 알람이 **배포 때마다** 울렸다. swap이 고장 난 게 아니라 제 역할을 하고 있다는 신호였지만, 뒤집어 보면 매 배포마다 빌드가 EC2 메모리를 swap까지 밀어붙인다는 뜻이었다. swap을 키우는 건 완충재를 두껍게 까는 일일 뿐이고, 코드 베이스가 자라면 빌드 피크 메모리도 같이 자란다.

진짜 약한 고리는 "빠듯한 RAM"이 아니라 **"EC2 위에서 빌드한다"** 쪽이었다. 빌드를 메모리가 넉넉한 곳으로 옮기면 전제 자체가 사라진다.

```
[기존] GitHub Actions → SSH → EC2에서 git pull → EC2에서 docker build → 실행
[변경] GitHub Actions에서 docker build → 이미지를 EC2로 전송 → EC2는 실행만
```

## ECR 대신 SSH 전송을 택한 이유

앞 글에서는 장기 개선책으로 "러너에서 빌드하고 ECR에 push"를 적어뒀다. 빌드를 옮기는 방향은 그대로 가져갔지만, ECR은 쓰지 않았다.

| ECR이 주는 가치 | 우리 상황 |
| --- | --- |
| 여러 노드가 같은 이미지를 pull | 인스턴스는 **1대** |
| 이미지 버전 관리·롤백 | 버전별 이미지를 보관하지 않고 항상 `latest`로 교체 |
| 빌드와 배포를 잇는 중앙 저장소 | 러너에서 EC2로 가는 **SSH 통로가 이미 있음** |
| 운영 부담 | 비용은 미미하지만 레포지토리·인증·라이프사이클 정책이 관리 대상으로 추가됨 |

ECR의 가치는 "여러 곳에, 여러 버전을, 나중에 다시" 가져다 쓰는 데 있다. 우리는 "한 곳에, 지금 이 이미지를, 한 번" 가져다 놓으면 끝이었다. 필요한 건 레지스트리가 아니라 전송 수단 하나였다.

## 파이프라인 구성

### 1. 러너에서 빌드

레지스트리에 올리지 않으므로 `push: false`, 러너의 로컬 Docker에 적재하도록 `load: true`를 준다. 캐시는 GitHub Actions 캐시(`type=gha`)를 쓴다.

```yaml
- name: Docker 이미지 빌드 (GitHub Actions 러너)
  uses: docker/build-push-action@v5
  with:
    context: .
    file: ./Dockerfile.production
    push: false
    load: true
    tags: ${{ env.IMAGE_NAME }}:latest
    cache-from: type=gha
    cache-to: type=gha,mode=max
```

### 2. 이미지를 EC2로 스트리밍 전송

```bash
docker save ${{ env.IMAGE_NAME }}:latest | gzip | \
  ssh -i /tmp/ephemeral_key \
      -o StrictHostKeyChecking=no \
      -o ServerAliveInterval=30 \
      -o ServerAliveCountMax=10 \
      ubuntu@${{ secrets.EC2_HOST }} \
      'docker load'
```

`docker save`가 이미지를 tar 스트림으로 내보내고, `gzip`이 압축하고, `ssh`가 EC2의 `docker load` 표준 입력에 그대로 연결한다. 파일로 저장한 뒤 `scp`로 보내는 방식과 결과는 같지만, **러너와 EC2 어디에도 중간 tar 파일이 남지 않는다.** 디스크가 빠듯한 EC2에서는 이 점이 중요했다.

### 3. EC2는 받아서 실행만

```bash
cd ~/app
git fetch "https://x-access-token:${TOKEN}@github.com/${REPO}.git" "${REF}"
git checkout -B "${REF}" FETCH_HEAD   # compose 파일 최신화

AVAIL_KB=$(df / --output=avail | tail -1)
if [ "$AVAIL_KB" -lt 2097152 ]; then  # 디스크 여유 2GB 미만이면 중단
  echo "❌ 디스크 여유 부족"
  exit 1
fi

docker compose -f docker-compose-prod.yml up -d
docker image prune -f
```

EC2 스크립트에서 `docker build`가 통째로 빠졌다. 빌드를 감시하던 `vmstat`·`free` 모니터링과 `docker builder prune`도 함께 들어냈고, SSH 타임아웃도 `30m`에서 `10m`으로 줄였다.

### 4. SSH 통로는 배포할 때만 연다

- 러너의 공인 IP만 **보안 그룹 22번 포트에 한시적으로 추가**한다.
- 매 실행마다 **임시 ed25519 키를 만들고** `ec2-instance-connect`로 공개키를 주입한다.
- 작업이 끝나면 `if: always()`로 보안 그룹 규칙과 키를 정리한다.

상시 열린 포트도 고정 키도 없이, 배포하는 그 러너에게만 통로가 열린다. 호스트 키 검사를 끈 것(`StrictHostKeyChecking=no`)도 이 전제 위에서 내린 선택이다. ECR을 썼다면 인증 체계를 하나 더 구성해야 했겠지만, 이 통로 하나로 전송과 배포가 모두 해결됐다.

## appleboy/ssh-action을 raw ssh로 바꾼 이유

처음에는 배포 실행 단계에 `appleboy/ssh-action`을 썼다. 그러다 우리 코드와 상관없는 곳에서 배포가 깨졌다.

```
Run appleboy/ssh-action@v1
Downloading drone-ssh-1.8.2-linux-amd64 from https://github.com/appleboy/drone-ssh/releases/download/v1.8.2
curl: (22) The requested URL returned error: 504
Failed to download drone-ssh-1.8.2-linux-amd64 ... Please check the URL and your network connection.
```

이 액션은 실행할 때마다 GitHub Releases에서 `drone-ssh` 바이너리를 내려받는다. 그날 Releases가 504를 반복하자 SSH 키도 EC2도 멀쩡한데 배포가 멈췄다. **편의 액션 안에 숨어 있던 런타임 다운로드가 배포 경로의 단일 장애점**이었던 셈이다.

raw `ssh`는 러너에 기본 설치돼 있어 다운로드가 없다. 이미지 전송 단계는 처음부터 raw `ssh`였으니 배포 실행도 같은 방식으로 맞췄다.

```yaml
- name: EC2 배포 실행
  timeout-minutes: 10
  run: |
    ssh -i /tmp/ephemeral_key \
        -o StrictHostKeyChecking=no \
        -o ServerAliveInterval=30 \
        -o ServerAliveCountMax=10 \
        ubuntu@${{ secrets.EC2_HOST }} << 'ENDSSH'
    set -euo pipefail
    cd ~/app
    # ... 배포 스크립트 ...
    ENDSSH
```

## 결과와 트레이드오프

**swap 알람이 멈췄다.** EC2에서 메모리를 몰아 쓰던 빌드가 사라졌으니 swap을 건드릴 메모리 압박도 생기지 않는다. 스래싱을 "재발하지 않게 막은" 앞 글과 달리, 이번에는 빌드발 스래싱이 일어날 조건 자체를 없앴다.

대신 배포 시간이 늘었다. 성공한 배포 워크플로 실행을 단계별로 집계한 결과다.

| | EC2 빌드 (2026년 5월) | 러너 빌드 (2026년 6월) |
| --- | --- | --- |
| 배포 전체 (중앙값) | 4.8분 (52회) | 7.2분 (76회) |
| 빌드 | 약 4.1분 (EC2 배포 실행 단계에 포함) | 5.5분 |
| 이미지 전송 | 없음 | 0.7분 |

처음에는 새로 생긴 전송 구간이 시간을 잡아먹을 거라고 예상했는데, 실제로 전송은 1분이 채 걸리지 않았다. **늘어난 시간의 대부분은 러너의 빌드 시간**이었다. EC2에는 이전 빌드의 레이어 캐시가 디스크에 그대로 남아 있었지만, 러너는 매번 새 머신에서 GitHub Actions 캐시를 내려받아 빌드하기 때문으로 보인다. 다음 개선은 캐시 전략 쪽이다.

그 밖에 남은 비용도 있다.

- **러너 사용량:** 빌드가 GitHub Actions 사용량에 잡힌다.
- **이미지 버전 관리의 부재:** 인스턴스가 늘거나 버전별 롤백이 필요해지면 이 방식은 한계에 부딪힌다. 그때가 ECR을 도입할 시점이다.

배포가 2.4분 느려진 건 분명한 손해다. 그래도 그 대가로 "인스턴스를 재부팅해야 살아나는" 종류의 장애를 없앴고, 남은 비용은 EC2 메모리와 무관한 캐시 튜닝의 문제로 옮겨 갔다.

<Callout type="info">
**측정 방법**

`gh run list`로 배포 워크플로의 성공 실행을 모으고, `gh run view --json jobs`로 단계별 시작·종료 시각을 받아 월별 중앙값을 냈다. 전환 시점에 걸친 며칠은 두 방식이 섞여 있어 월 단위로 나눴다.

</Callout>

## 마무리

앞 글에서 swap을 두고 "완화"라고 적었던 게 내내 마음에 걸렸는데, 빌드를 EC2 밖으로 옮기고 나서야 "해결"이라고 쓸 수 있게 됐다. 교과서는 ECR을 가리켰지만, 지금 규모에 필요한 건 이미지를 한 번 실어 나를 통로 하나였다.
