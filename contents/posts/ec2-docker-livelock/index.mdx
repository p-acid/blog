서비스를 운영하다 보면 "분명 인스턴스는 살아 있는데, 아무것도 응답하지 않는" 상황을 만날 때가 있다.

이번에 마주한 문제도 그랬다. GitHub Actions를 통해 EC2에서 Docker 빌드를 수행하던 중, Next.js production build 단계에서 로그가 멈췄고 SSH 접속까지 되지 않았다. 그런데 AWS 콘솔에서는 인스턴스가 여전히 `running` 상태로 보였다.

처음에는 단순한 빌드 지연이나 OOM을 의심했다. 하지만 커널 로그에 OOM 흔적은 없었고, CPU 크레딧도 충분했다. 결국 이 문제는 **메모리 압박과 EBS I/O 병목이 겹치면서 사용자 공간 프로세스가 응답하지 못한, livelock에 가까운 간헐적 정지 상황**으로 판단했다.

그리고 이 상황은 **4GB swap을 추가한 뒤 동일한 조건에서 빌드가 완료되는 것**을 확인하면서 완화할 수 있었다.

<Callout type="info">
**이 글에서 말하는 livelock**

이 글에서 `livelock`은 커널 내부 상태를 엄밀하게 증명한 용어라기보다, 운영 관찰 관점에서의 표현이다. 실제로 확인한 것은 다음과 같다.

- 빌드 프로세스뿐 아니라 SSH까지 응답하지 않음
- OOM Kill 로그가 없음
- EC2 상태 체크는 정상으로 표시됨
- EBS `VolumeQueueLength`가 증가함
- swap 없이 재현하면 다시 SSH가 막힘
- swap을 켠 동일 조건에서는 빌드가 완료됨

따라서 본문에서는 "livelock 확정"보다는 **livelock에 가까운 사용자 공간 정지 상태**로 다룬다.

</Callout>

## 증상: 빌드는 멈추고, SSH도 응답하지 않았다

문제는 GitHub Actions 배포 중 발생했다. Docker build 로그는 Next.js production build 단계에서 더 이상 진행되지 않았다.

```bash
#13 2.034   Creating an optimized production build ...
            ← 여기서 4분 넘게 멈춤
```

단순히 빌드가 오래 걸린 것이라면 SSH로 들어가 상태를 확인할 수 있어야 했다. 하지만 SSH 접속도 되지 않았다. 반면 AWS 콘솔에서는 인스턴스가 계속 `running` 상태였고, EC2 상태 체크도 실패하지 않았다.

이 지점에서 문제를 단일 빌드 프로세스의 hang으로 보기 어려워졌다. SSH까지 응답하지 않는다는 건, 빌드 프로세스 하나가 느린 것이 아니라 **사용자 공간 프로세스 전반이 커널의 I/O 응답을 기다리며 멈춘 상태**일 가능성이 높았기 때문이다.

## 먼저 배제한 것들

가장 먼저 CPU와 OOM을 확인했다.

### CPU 크레딧은 충분했다

인스턴스는 t2 계열이었기 때문에 CPU 크레딧 소진을 먼저 의심했다. 하지만 CloudWatch의 `CPUCreditBalance`는 충분했다.

```bash
CPUCreditBalance: 576
```

CPU 크레딧이 바닥나서 빌드가 느려진 상황은 아니었다.

### OOM Kill 흔적도 없었다

Next.js 빌드는 메모리를 많이 사용하기 때문에 OOM Kill도 의심했다. 확인은 커널 로그에서 했다.

```bash
sudo dmesg | grep -i oom
sudo journalctl -k | grep -i "oom\|killed"
```

하지만 OOM 관련 로그는 없었다. OOM Kill이 발생했다면 프로세스가 강제로 종료되고 로그가 남아야 한다. 이번 경우는 프로세스가 죽은 것이 아니라, 시스템이 응답하지 못하는 상태에 가까웠다.

## 의심 지점: 메모리 압박과 EBS I/O 병목

문제가 발생한 인스턴스의 메모리 상태는 다음과 같았다.

```bash
              total        used        free      shared  buff/cache   available
Mem:           3.8Gi       1.0Gi       290Mi       0.0Ki       2.5Gi       2.5Gi
Swap:             0B          0B          0B
```

여기서 `free`만 보면 여유 메모리가 거의 없어 보이지만, Linux에서는 `available`을 함께 봐야 한다. `buff/cache`는 필요하면 회수 가능한 페이지 캐시이기 때문에, 그 자체를 곧바로 "부족한 메모리"로 해석하면 안 된다.

다만 이번 문제에서는 이 페이지 캐시 회수 과정이 중요했다. 빌드 중 Node.js 메모리 사용량이 증가하면 커널은 페이지 캐시를 회수한다. 이때 dirty page write-back이나 캐시 재접근이 발생하고, EBS 성능이 충분하지 않으면 이 회수 과정 자체가 I/O 병목이 될 수 있다.

문제 발생 시각의 EBS 지표에서도 단서가 있었다.

```bash
정상 상태:                  VolumeQueueLength ≈ 0
hang 발생 시각:             VolumeQueueLength = 1.68
```

`VolumeQueueLength`는 EBS 앞에서 대기 중인 I/O 요청의 평균 큐 길이다. 이 값 하나만으로 IOPS 포화를 단정할 수는 없지만, 평소 거의 0에 가깝던 값이 SSH 불가 시점에 증가했다는 점은 **EBS I/O 병목 가능성**을 높여주는 단서였다.

정리하면 당시 의심한 흐름은 다음과 같다.

```bash
Next.js Docker build 시작
→ Node.js / webpack / TypeScript 메모리 사용량 증가
→ 커널이 페이지 캐시 회수 시작
→ dirty page write-back 또는 캐시 재접근으로 EBS I/O 증가
→ EBS 앞에 I/O 요청이 쌓임
→ 사용자 공간 프로세스가 I/O 대기 상태에 묶임
→ SSH까지 응답하지 않음
→ 재부팅으로만 복구
```

<Callout type="info">
**왜 AWS 콘솔에서는 정상으로 보였을까**

EC2 상태 체크가 정상이라는 것은 인스턴스나 가상화 레벨에서 문제가 감지되지 않았다는 뜻에 가깝다. SSH가 정상 응답한다는 의미는 아니다.

사용자 공간 프로세스가 I/O 대기에 묶여 있거나, OS 내부에서 병목이 발생한 경우에는 상태 체크가 정상이어도 실제 서비스나 SSH는 응답하지 않을 수 있다.

</Callout>

## 왜 간헐적으로만 발생했을까

이 문제는 매번 발생하지 않았다. 어떤 배포는 성공했고, 어떤 배포는 같은 지점에서 멈췄다.

간헐적으로 발생한 이유는 **빌드 시점의 메모리 여유와 페이지 캐시 상태가 매번 달랐기 때문**으로 보였다.

```bash
재부팅 직후 배포
→ 페이지 캐시가 적음
→ 메모리 회수 부담이 작음
→ 빌드 성공

운영 후 며칠 뒤 배포
→ Docker 레이어와 파일 캐시가 누적됨
→ 빌드 중 페이지 캐시 회수 부담 증가
→ EBS I/O 대기 증가
→ SSH까지 응답하지 않는 정지 상태 발생
```

즉, 특정 코드 한 줄이 곧바로 문제를 만든 것이라기보다, 작은 인스턴스에서 Docker build를 직접 수행하는 구조가 이미 임계점에 가까웠고, 빌드 시점의 캐시 상태와 메모리 압박이 겹칠 때 문제가 터진 것으로 판단했다.

## 검증 1: swap 없이 동일 조건을 재현했다

가설을 확인하기 위해 먼저 swap을 끈 상태에서 강한 빌드 조건을 만들었다.

```bash
sudo swapoff /swapfile
free -h

nohup vmstat 2 > /tmp/livelock-no-swap.log 2>&1 &

docker compose -f docker-compose-prod.yml build --no-cache
```

`--no-cache`를 사용했기 때문에 실제 배포보다 더 가혹한 조건이었다. 모든 레이어를 다시 빌드하면서 메모리와 디스크 I/O 부담이 커진다.

결과는 기존 증상과 거의 같았다.

```bash
빌드 결과: hang
SSH: 접속 불가
복구 방법: AWS 콘솔에서 Reboot
VolumeQueueLength 최대값: 27.62
```

실제 장애 시점의 `VolumeQueueLength`는 1.68이었고, 재현 실험에서는 27.62까지 증가했다. 실험 조건이 더 가혹했기 때문에 더 큰 값이 나온 것으로 보인다.

중요한 건, swap이 없는 상태에서 빌드가 다시 SSH 불가 상태를 만들었다는 점이다.

## 검증 2: swap 4GB를 켠 뒤 동일 조건을 다시 실행했다

다음은 swap을 켠 상태에서 같은 빌드를 다시 실행했다.

```bash
sudo fallocate -l 4G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

free -h
```

swap 적용 후 메모리 상태는 다음과 같았다.

```bash
              total        used        free      shared  buff/cache   available
Mem:           3.8Gi       1.0Gi       300Mi       0.0Ki       2.5Gi       2.5Gi
Swap:          4.0Gi          0B       4.0Gi
```

그리고 동일하게 빌드를 실행했다.

```bash
nohup vmstat 2 > /home/ubuntu/livelock-with-swap.log 2>&1 &

docker compose -f docker-compose-prod.yml build --no-cache
```

이번에는 빌드가 완료됐다. SSH도 끊기지 않았다.

`vmstat` 로그에서 swap은 약 208MB 정도 사용됐다.

```bash
wa:0%  swpd:212992KB so:0
wa:0%  swpd:212992KB so:0
wa:1%  swpd:212992KB so:0
wa:18% swpd:212992KB so:0
wa:30% swpd:212992KB so:0
wa:8%  swpd:212992KB so:0
wa:3%  swpd:212992KB so:0
wa:0%  swpd:212992KB so:0
```

`wa%`는 I/O wait 비율이다. 순간적으로 30%까지 올라갔지만, 지속적으로 치솟지 않고 다시 안정화됐다. swap이 208MB 정도의 부족분을 흡수하면서 페이지 캐시 회수와 EBS I/O 대기가 폭발하는 상황을 막아준 것으로 보인다.

<Callout type="warning">
**swap이 EBS I/O를 없애는 것은 아니다**

swapfile도 EBS 위에 있다면 swap 사용 역시 디스크 I/O를 만든다. 따라서 swap은 근본적인 I/O 최적화 수단이 아니다.

다만 이번 케이스에서는 swap 사용량이 약 208MB로 제한적이었고, 그 정도의 여유 공간이 메모리 압박의 피크를 흡수해 사용자 공간 전체가 I/O 대기에 묶이는 상황을 피하게 해줬다.

</Callout>

## swap 유무에 따른 결과 비교

| 항목 | swap 없음 | swap 4GB |
| --- | --- | --- |
| 빌드 결과 | hang | 완료 |
| SSH | 접속 불가 | 유지 |
| `VolumeQueueLength` | 최대 27.62 | 정상 범위 |
| `wa%` | 측정 지속 불가 | 최대 30% 후 안정화 |
| swap 사용량 | 0 | 약 208MB |
| 복구 방법 | AWS 콘솔 Reboot | 별도 복구 불필요 |

이 비교를 통해 문제를 이렇게 정리했다.

```bash
swap 없음
→ 메모리 피크를 흡수할 완충 공간이 없음
→ 페이지 캐시 회수와 EBS I/O 대기가 한 번에 몰림
→ SSH까지 응답하지 않는 livelock 유사 상태 발생

swap 있음
→ 약 208MB의 메모리 피크를 swap이 흡수
→ I/O wait가 순간적으로 증가하지만 회복 가능
→ 빌드 완료, SSH 유지
```

## 실제 적용한 조치

핵심 조치는 swap 4GB 추가였다.

```bash
sudo fallocate -l 4G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

printf '/swapfile none swap sw 0 0\n' | sudo tee -a /etc/fstab
```

그리고 운영 중 swap을 너무 적극적으로 사용하지 않도록 `swappiness`를 낮췄다.

```bash
echo 'vm.swappiness=10' | sudo tee -a /etc/sysctl.conf
sudo sysctl -p
```

`vm.swappiness=10`은 swap을 최후의 완충 장치에 가깝게 사용하기 위한 설정이다. 메모리가 충분한 상황에서도 swap을 적극적으로 쓰게 만들고 싶지는 않았다.

이후 확인 명령은 다음과 같이 정리했다.

```bash
free -h
swapon --show
cat /proc/sys/vm/swappiness
```

## 함께 적용한 보조 조치

이 글의 핵심은 swap으로 간헐적 livelock을 완화한 내용이지만, 같은 문제가 다시 발생할 가능성을 줄이기 위해 빌드 주변의 메모리·I/O 부담도 함께 줄였다.

### `.dockerignore`에 `.next` 추가

로컬 빌드 산출물인 `.next`가 Docker build context에 포함되고 있었다. 배포 시점마다 불필요한 파일이 Docker daemon으로 전송되면 디스크 I/O와 빌드 시간이 늘어난다.

```bash
before: build context 893MB
after:  build context 54MB
```

`.dockerignore`에는 다음 항목을 추가했다.

```dockerignore
.next
node_modules
.git
```

### Node.js heap 상한 조정

기존에는 Node.js heap 상한을 3GB로 두고 있었다.

```bash
before: --max-old-space-size=3072
after:  --max-old-space-size=2048
```

인스턴스 전체 메모리가 3.8GiB인 상황에서 Node.js 하나가 3GB까지 사용할 수 있게 두는 것은 부담이 컸다. heap 상한을 2GB로 낮춰 시스템 전체가 사용할 최소 여유를 남기는 방향으로 조정했다.

### Docker prune 범위 축소

기존에는 배포마다 Docker build cache까지 모두 삭제했다.

```bash
docker system prune -af
```

이 방식은 디스크를 정리하는 데는 효과적이지만, 다음 빌드에서 모든 것을 다시 다운로드하고 다시 컴파일하게 만든다. 결과적으로 빌드 시간과 I/O 부담이 커진다.

이후에는 이미지 정리와 build cache 상한 관리로 나눴다.

```bash
docker image prune -f
docker builder prune --keep-storage 3g -f
```

### BuildKit cache mount 사용

npm 캐시와 Next.js 캐시를 BuildKit cache mount로 분리했다.

```dockerfile
RUN --mount=type=cache,target=/root/.npm \
    npm ci

RUN --mount=type=cache,target=/app/.next/cache \
    NODE_OPTIONS="--max-old-space-size=2048" npm run build
```

이 조치는 livelock의 직접 해결책은 아니지만, 빌드가 메모리 압박 상태에 머무는 시간을 줄이는 데 도움이 됐다.

```bash
Cold build: 244초
Warm build: 86초
개선폭: -158초
```

## 이번 문제에서 얻은 기준

이번 문제는 단순히 "swap을 켜면 된다"로 끝낼 문제는 아니었다. 오히려 작은 EC2 인스턴스에서 production build까지 직접 수행하는 구조가 얼마나 쉽게 임계점에 닿을 수 있는지 확인한 사례에 가까웠다.

정리하면 다음 기준이 남았다.

- SSH까지 응답하지 않으면 단일 프로세스 문제가 아니라 사용자 공간 전반의 정지를 의심한다.
- OOM Kill 로그가 없다면 메모리 부족만으로 단정하지 않는다.
- `free`보다 `available`을 함께 보고, `buff/cache` 회수 과정에서 I/O가 발생할 수 있음을 고려한다.
- EC2 상태 체크가 정상이어도 OS 내부 I/O 병목은 별도로 확인해야 한다.
- EBS 병목 의심 시 `VolumeQueueLength`를 단독으로 보지 말고, I/O wait와 재현 실험 결과를 함께 본다.
- swap은 성능 개선책이 아니라, 메모리 피크를 흡수하기 위한 안전장치로 사용한다.

## 마무리

이번 문제의 핵심은 "빌드가 느렸다"가 아니었다.

작은 EC2 인스턴스에서 Docker build를 직접 수행하던 중, Next.js 빌드의 메모리 피크와 페이지 캐시 회수, EBS I/O 대기가 겹치면서 사용자 공간 프로세스가 응답하지 못하는 상황이 간헐적으로 발생했다.

swap 4GB를 추가한 뒤 같은 조건에서 빌드가 완료됐고, 실제 사용된 swap은 약 208MB였다. 이 결과를 통해 swap이 메모리 피크를 흡수해 livelock에 가까운 정지 상황을 완화했다는 결론을 얻었다.

물론 swap은 근본적인 해결책은 아니다. 장기적으로는 빌드를 EC2 밖에서 수행하거나, EBS를 gp3로 전환하거나, 빌드 메모리 사용량을 지속적으로 측정하는 방향이 더 안전하다.

다만 이번 케이스에서는 작은 완충 공간 하나가 시스템 전체 정지를 막아줬다.
