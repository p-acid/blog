서비스를 운영하다 보면 어느 순간 "이게 왜 지금 갑자기?"라는 의문을 던지게 만드는 문제들이 등장한다.
배포 파이프라인이 갑자기 멈추거나, 정상이라 알고 있던 인스턴스가 통째로 응답을 거부하는 식의 일들이다.

> 그리고 보통 그런 일은 가장 바쁠 때 일어난다.

이번 포스팅은 GitHub Actions를 통한 EC2 Docker 빌드가 Next.js 컴파일 단계에서 멈춰버린 사건의 디버깅 기록이다.
원인은 **메모리 압박이 EBS I/O 포화로 이어져 발생한 D-state thrashing**(통상 livelock이라고도 불리는, 사용자 공간 프로세스 대부분이 정지하는 상태)이었고, 결국 **swap 메모리 추가**로 막아냈다.
원인을 찾기까지의 흐름과, 해법이 실제로 동작하는지 직접 재현해 검증한 과정까지 함께 정리했다.

## 어느 날 배포가 멈췄다

발단은 평소와 다르지 않은 배포 알림이었다. GitHub Actions 로그에는 분명 빌드가 진행 중이었는데, 어느 순간부터 출력이 멈춰 있었다.

```
#13 2.034   Creating an optimized production build ...
            ← 여기서 4분 넘게 멈춤
```

이상한 점은, **AWS 콘솔에 접속해보면 인스턴스 상태가 멀쩡하게 `running`으로 표시**된다는 것이었다.
SSH로 직접 접속을 시도해봐도 아무런 응답이 없었다. 결국 인스턴스를 재시작하니 정상 동작했고, 며칠 뒤 같은 일이 또 반복됐다.

처음에는 단순히 Next.js 빌드가 느린 줄 알았다. `command_timeout: 30m`을 넉넉히 잡아뒀는데도 멈춘다는 게 이상했고,
무엇보다 **SSH 자체가 응답하지 않는다는 점**이 가장 큰 단서였다.

빌드 프로세스만 느린 게 아니라, 사용자 공간 프로세스 전반이 응답하지 못하는 상태로 보였다.

## 가설 1. CPU 크레딧이 바닥났을까

가장 먼저 떠올린 건 t2 인스턴스의 CPU 크레딧 문제였다.
t2 시리즈는 버스트 크레딧 방식이라 크레딧이 소진되면 베이스라인 성능(t2.medium 기준 40%)으로 떨어진다.
빌드 같은 CPU 집약적 작업이라면 충분히 가능성이 있었다.

CloudWatch에서 `CPUCreditBalance` 지표를 확인했다.

```
CPUCreditBalance: 576 (만충 상태)
```

576이면 거의 최대치다. 크레딧 문제는 아니었다. **가설 1 탈락.**

## 가설 2. OOM Kill일까

Next.js 빌드는 메모리를 많이 먹는다.
`NODE_OPTIONS=--max-old-space-size=3072`로 힙 상한을 3GB까지 허용하고 있었는데, t2.medium의 RAM은 3.8GB(가용 2.9GB)다.
Node.js가 메모리를 다 쓰면 커널이 프로세스를 강제로 종료시킬 가능성이 충분했다.

근데 OOM Kill이 일어나면 반드시 커널 로그에 흔적이 남는다.

```bash
sudo dmesg | grep -i oom
sudo journalctl -k | grep -i "oom\|killed"
```

아무것도 없었다. 게다가 OOM Kill이 일어났다면 프로세스가 죽고 시스템은 다시 응답해야 하는데,
이번 케이스는 SSH까지 막혀 아무것도 안 됐다. **가설 2도 탈락.**

## 이상한 점들을 정리해보면

가장 흔한 두 가지 시나리오가 모두 빗나갔으니, 한 발 물러나 지금까지 모은 단서들을 다시 펼쳐놓고 살펴보기로 했다.

| 관찰 | 의미 |
| --- | --- |
| 빌드가 항상 같은 위치(`Creating an optimized production build...`)에서 멈춤 | 특정 단계에서 트리거되는 무언가가 있다 |
| SSH도 응답하지 않음 | 빌드 프로세스만의 문제가 아니다 |
| AWS 콘솔은 인스턴스를 "정상"으로 인식 | 하드웨어 레벨은 살아있다 |
| OOM Kill 로그 없음 | 프로세스가 죽은 게 아니다 |
| 재시작하면 복구됨 | 재시작 시 초기화되는 무언가가 원인이다 |
| 간헐적으로 발생 | 특정 조건이 겹쳐야 한다 |

여기서 핵심은 **SSH까지 막혔다**는 점이었다.

<Callout type="info">
**SSH가 응답하지 않는다는 건 무슨 의미일까**

빌드 프로세스 하나만의 문제였다면 SSH는 살아있어야 한다.
SSH 데몬까지 응답하지 못한다는 건 커널 자체가 멈췄다기보다,
**거의 모든 사용자 공간 프로세스가 커널의 I/O 응답을 기다리는 D state(uninterruptible sleep)에 빠져 있다**는 신호에 가깝다.

</Callout>

이런 종류의 시스템 전반 정지는 흔치 않은데, 그 중 하나가 바로 **광범위한 I/O wait로 인한 사용자 공간 정지**다.
`wa%`(CPU가 I/O 완료를 기다리며 노는 비율)가 거의 100%까지 치솟고, 대부분의 프로세스가 `D state`로 진입해 `kill` 명령도 듣지 않는 상태다.
OOM과 달리 커널 로그에 아무 흔적이 남지 않고, 재시작이 거의 유일한 복구 수단이 된다.

자연스럽게 다음 질문이 따라왔다.

> 그렇다면 무엇이 I/O를 막히게 했을까?

## 진짜 원인은 EBS I/O 포화였다

EBS였다. 정확히는, 메모리 압박이 EBS I/O 포화로 이어져 발생한 **D-state thrashing** 상태였다.

<Callout type="info">
**D-state thrashing이란**

리눅스에서 프로세스는 I/O 요청을 보내고 응답을 기다리는 동안 `D state(uninterruptible sleep)`에 머문다.
평상시에는 일부 프로세스만 잠깐 D state에 들어갔다 빠르게 빠져나오는데,
디스크 I/O가 포화되면 점점 더 많은 프로세스가 이 상태에 쌓이고, 결국 거의 모든 사용자 공간 프로세스가 D state에서 빠져나오지 못해 시스템 전반이 정지한 것처럼 보이게 된다. 이 현상을 **D-state thrashing**이라고 부른다.

OOM Kill처럼 커널 로그에 흔적이 남지도, `kill` 명령으로 풀리지도 않는다는 점이 특징이다. 재시작이 거의 유일한 복구 수단이다.

</Callout>

이 가설을 뒷받침할 단서가 있을지 우선 CloudWatch의 EBS 지표부터 뒤져봤다.

**`VolumeQueueLength`** 는 EBS I/O 요청 대기 큐의 길이를 나타내는 지표다. 정상이라면 거의 0에 가까워야 한다.

```
정상 상태:              ≈ 0
hang 발생 시각(KST 15:19): 1.68
```

hang이 발생한 정확한 시각에 `VolumeQueueLength`가 1.68로 치솟아 있었다.
**EBS 앞에 평균 1.68개의 I/O 요청이 쌓여있다는 의미고, IOPS 한계에 도달했다는 명백한 신호였다.**

그렇다면 어떻게 거기까지 도달했는지, 흐름을 정리해보면 다음과 같다.

```
[환경]
RAM: 3.8GB (시스템 점유분 제외 시 가용 약 2.9GB)
Swap: 없음
buff/cache: 2.3GB (Docker 레이어 등이 페이지 캐시에 올라가 있음)
EBS: gp2 (버스트 크레딧 소진 시 베이스라인 100 IOPS)
NODE_OPTIONS: --max-old-space-size=3072

[흐름]
Next.js 빌드 시작 → Node.js 힙 급증 (~2GB+)
→ free 메모리 부족 → 커널의 페이지 캐시 회수(reclaim) 시작
  · dirty 페이지는 EBS에 write-back
  · clean 페이지는 해제 후 다시 접근 시 EBS에서 재페치
→ EBS IOPS 한계 도달 → I/O 요청 대기 큐 폭증
→ 대부분의 사용자 공간 프로세스가 D state로 진입
→ SSH 포함 사용자 공간 전체 응답 불가
→ AWS의 인스턴스 상태 체크는 가상화 레이어 기준이라 "정상"으로 표시
→ 재시작으로 RAM·페이지 캐시가 초기화되어야만 복구
```

### 왜 간헐적으로만 발생했을까

문제가 인지된 시점에는 "그동안 잘 됐는데 왜 갑자기?"라는 의문이 컸다.

원인은 두 가지 조건이 동시에 충족될 때만 D-state thrashing이 발현된다는 점에 있었다.

1. **프로젝트 규모 증가** — 릴리즈를 거듭하면서 Next.js 빌드의 피크 힙 사용량이 서서히 증가했고, 어느 순간 가용 메모리 한계에 닿게 됐다.
2. **페이지 캐시 누적량 변동** — 재시작 직후에는 buff/cache가 적지만, 운영하다 보면 Docker 레이어 등이 페이지 캐시에 올라오며 점점 쌓인다. 빌드 시점에 캐시가 얼마나 쌓여 있느냐에 따라 thrashing 발생 여부가 결정됐다.

```
재시작 직후 배포:    페이지 캐시 적음 → 여유 있음 → 빌드 성공
며칠 후 배포:       페이지 캐시 2GB+ → 여유 없음 → D-state thrashing
```

### 그런데 왜 하필 이번 릴리즈에서 처음 터졌을까

위 두 조건이 모두 만족되는 시점이 왜 하필 v1.4.61이었는지는 별도로 짚어볼 필요가 있었다.
"규모가 점진적으로 증가"한다는 말은 너무 막연했고, 실제로 어떤 변화가 임계점을 넘기게 만들었는지 직접 확인하고 싶었다.

이전 정상 배포 버전(v1.4.60)과 hang이 발생한 v1.4.61의 코드 베이스를 비교해봤다.

| 버전 | `schema.ts` | TS 파일 수 | 비고 |
| --- | --- | --- | --- |
| v1.4.52 ~ v1.4.57 | 43,555줄 (1,085KB) | 1,198개 | **6버전 연속 동결** |
| v1.4.58 | 43,704줄 (+149) | 1,209개 (+11) | 누적 성장 재개 |
| v1.4.59 | 43,922줄 (+218) | 1,210개 (+1) | |
| v1.4.60 | 43,922줄 (동일) | 1,210개 (동일) | **변경 없음 → 정상** |
| **v1.4.61** | **44,197줄 (+275)** | **1,222개 (+12)** | **첫 hang 발생** |

세 가지 패턴이 보였다.

1. **`schema.ts` 단일 파일의 누적 성장** — OpenAPI 자동 생성 파일이라 한 번 늘어나면 줄지 않는다. v1.4.52~57 6버전 동안 동결돼 있다가 v1.4.58부터 다시 커지기 시작했고, v1.4.61에서 한 번에 +275줄(+10KB)이 들어갔다. 멤버십·얼리버드 구독 관련 신규 타입이 한꺼번에 추가된 영향이다.
2. **신규 TS 파일 12개 동시 추가** — 그 중 다수가 `next/link`, `next/navigation`, `@tanstack/react-query`, `overlay-kit`, `@heroicons/react` 등 무거운 패키지를 동시에 임포트하는 컴포넌트였다. webpack 모듈 그래프가 한 릴리즈에 광범위하게 확장됐다.
3. **`next.config.ts`에 `images.remotePatterns` 추가, `global.d.ts` 전역 타입 확장** — 단독으로는 미미하지만, 이미 임계점 근방인 상태에서 marginal한 추가 부담으로 작용했다.

여기서 중요한 건 단순히 "275줄 더 파싱"이 아니라는 점이다.
TypeScript 컴파일러는 44K 라인짜리 `schema.ts`의 AST 전체를 메모리에 올린 뒤, 이 파일의 `Schema<"...">` 제네릭을 참조하는 1,222개 파일을 타입 추론한다.
신규 컴포넌트가 추가될수록 컴파일 메모리 사용량은 선형이 아니라 **승수 효과**로 증가한다.

```
v1.4.52~57:   schema.ts 동결 → 컴파일 메모리 안정
v1.4.58~60:   누적 증가, 여유 메모리 점진적으로 줄어듦
v1.4.61:      schema.ts +275줄 × 신규 컴포넌트 +12개
              → webpack 피크 힙이 EC2 가용 RAM(2.9GB) 임계점 돌파
              + 배포 당일 페이지 캐시 2.3GB 누적 상태
              = D-state thrashing 첫 발생
```

운영 환경의 메모리 한계는 그대로인데, 소스 코드가 그 선을 야금야금 갉아먹다가 어느 순간 넘어선 것이다.
"왜 하필 지금"이라는 질문에 대한 답은 결국 **점진적 누적과 임계점**이라는 단순한 메커니즘이었다.

## 가설 검증: 직접 재현해보기

분석만으로는 부족했다. 실제로 같은 현상을 재현하고, swap을 추가했을 때 동작이 달라지는지 직접 확인해보고 싶었다.

### Phase 1. swap 없이 풀 빌드

```bash
# swap 비활성화
sudo swapoff /swapfile
free -h  # Swap: 0B 확인

# vmstat 기록 시작
nohup vmstat 2 > /tmp/livelock-no-swap.log 2>&1 &

# 빌드 실행
docker compose -f docker-compose-prod.yml build --no-cache
```

`--no-cache` 옵션을 붙이면 모든 레이어를 처음부터 빌드해 Node.js 피크 메모리가 더 높아진다.
실제 hang 시점보다 더 극단적인 조건이다.

결과는 명확했다.

- 빌드 `#12/16` 단계에서 중단
- 외부 SSH 접속 불가
- CloudWatch `VolumeQueueLength` 최대값 **27.62**
- 복구 방법: AWS 콘솔에서 Reboot

```
정상:               ≈ 0
실제 hang 시점:     1.68
Phase 1 재현 결과:  27.62
```

27.62는 27개 이상의 I/O 요청이 EBS 앞에 동시에 쌓여있다는 뜻이다.
`--no-cache` 조건이 실제 상황보다 가혹해서 더 큰 값이 나온 것이다.

<Callout type="info">
**재부팅 후 vmstat 로그가 사라진 이유**

Phase 1에서 `/tmp`에 기록했던 `vmstat` 로그는 재부팅 후 사라졌다.
Ubuntu 22.04의 `/tmp`는 (흔히 알려진 것과 달리) 기본적으로 `tmpfs`가 아니라 루트 파일시스템 상의 일반 디렉토리지만,
`systemd-tmpfiles`가 부팅 시 정리 정책에 따라 비워주기 때문에 결과적으로 휘발성처럼 동작한다.
Phase 2에서는 `/home/ubuntu/` 경로에 기록해 동일한 실수를 반복하지 않았다.

</Callout>

### Phase 2. swap 4GB로 동일 조건 재현

Phase 1으로 원인은 분명해졌지만, **swap이 정말 해결책으로 동작하는지는 별도로 검증해야 했다.**
원인 확정과 해법 검증은 별개의 문제이기 때문이다.

이번에는 swap을 켜고, **buff/cache는 오히려 더 극단적인 2.9GB**로 만들었다.
더 불리한 조건에서도 swap이 방어해주는지 확인하고 싶었다.

```bash
# buff/cache를 2.9GB로 강제로 채움
sudo bash -c 'find /var/lib/docker -type f -exec cat {} \; > /dev/null 2>&1' &
# free -h 로 2.9Gi 확인 후 종료

# swap 재활성화
sudo swapon /swapfile
free -h  # Swap: 4.0Gi 확인

# vmstat 기록 (재부팅에도 남는 경로)
nohup vmstat 2 > /home/ubuntu/livelock-with-swap.log 2>&1 &

# 동일한 빌드 명령
docker compose -f docker-compose-prod.yml build --no-cache
```

결과는 전혀 달랐다.

```
# vmstat 로그 발췌 (빌드 피크 구간)
wa:0%  swpd:212992KB so:0
wa:0%  swpd:212992KB so:0
wa:1%  swpd:212992KB so:0
wa:18% swpd:212992KB so:0   ← 순간 스파이크
wa:30% swpd:212992KB so:0   ← 최대 I/O wait
wa:8%  swpd:212992KB so:0
wa:3%  swpd:212992KB so:0
wa:0%  swpd:212992KB so:0   ← 안정화
```

- 빌드 정상 완료
- SSH 연결 유지
- swap 사용량 **208MB** (메모리 압박 흡수)
- `wa%`가 순간적으로 30%까지 올라갔다가 즉시 안정화

`wa%`는 CPU가 I/O 완료를 기다리며 노는 비율이다. Phase 1에서는 이 값이 99% 가까이 치솟아 사용자 공간 프로세스 대부분이 D state로 빠졌을 것으로 추정된다.

### 두 실험의 비교

| 항목 | Phase 1 (swap 없음) | Phase 2 (swap 4GB) |
| --- | --- | --- |
| 빌드 결과 | ❌ hang | ✅ 완료 |
| SSH | 차단 | 유지 |
| `VolumeQueueLength` 최대 | **27.62** | 정상 |
| `wa%` 최대 | 측정 불가 (SSH 차단) | **30%** (순간) |
| swap 사용량 | 0 | 208MB |
| 복구 방법 | AWS 콘솔 Reboot | 자동 완료 |

Phase 2가 페이지 캐시 조건이 **더 극단적**(2.9GB > 2.3GB)이었음에도 swap 208MB가 메모리 압박을 흡수해 EBS IOPS 포화를 막아낸 것이다.
**D-state thrashing의 원인과 swap의 효과가 동시에 검증된 순간이었다.**

## 적용한 개선사항

가설이 검증됐으니 이제 실질적인 조치를 적용할 차례였다.

### 1. EC2 swap 4GB 추가 (핵심 조치)

```bash
sudo fallocate -l 4G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

# 프로덕션 최적화: swap을 최후 수단으로만 사용
echo 'vm.swappiness=10' | sudo tee -a /etc/sysctl.conf
sudo sysctl -p
```

`vm.swappiness=10`은 커널이 swap을 적극적으로 사용하지 않도록 하는 설정이다.
기본값 60은 실제 서비스 성능이 저하될 수 있어, **정말 메모리가 부족한 순간에만 swap이 동작**하도록 조정했다.

### 2. `.dockerignore`에 `.next` 추가

매 빌드마다 893MB의 빌드 아티팩트가 Docker daemon으로 전송되고 있었다.
`.next` 폴더를 `.dockerignore`에 추가하니 54MB로 줄었다(-94%).

### 3. `NODE_OPTIONS` 조정

```
before: --max-old-space-size=3072  (가용 메모리 2.9GB 초과)
after:  --max-old-space-size=2048  (가용 메모리 내로 조정)
```

### 4. Docker 정리 방식 변경

```bash
# before: 빌드 캐시까지 전부 삭제
docker system prune -af

# after: 이미지만 정리하고 빌드 캐시는 보존 (상한 3GB)
docker image prune -f
docker builder prune --keep-storage 3g -f
```

매 배포마다 빌드 캐시를 날리면 `npm install`부터 전부 다시 해야 한다. 캐시를 보존하되 누적 상한만 두는 방향으로 바꿨다.

### 5. Dockerfile BuildKit 캐시 마운트

```dockerfile
RUN --mount=type=cache,target=/root/.npm \
    npm ci

RUN --mount=type=cache,target=/app/.next/cache \
    NODE_OPTIONS="--max-old-space-size=2048" npm run build
```

`--mount=type=cache`는 BuildKit이 제공하는 캐시 마운트 기능이다.
이미지 레이어에 포함되지 않으면서, 빌드 사이에 호스트 디스크에 보존되는 별도의 캐시 볼륨을 제공한다.
이를 통해 npm tarball을 재다운로드하지 않고, `.next/cache`를 재사용해 webpack이 변경된 파일만 다시 컴파일한다.

```
Cold 빌드 (캐시 없음):  244초 (4분 4초)
Warm 빌드 (캐시 재사용): 86초 (1분 26초)
개선:                  -158초 (-65%)
```

빌드 시간 65% 단축은 단순한 성능 개선이 아니라, **Node.js가 메모리 압박 상태에 머무는 시간이 그만큼 줄었다**는 의미이기도 했다.

## 앞으로 어떤 개선을 적용할 것인가

지금까지의 조치(swap 추가, BuildKit 캐시 마운트, `.dockerignore` 보정 등)는 임계점에서 한 발 물러서게 해주는 안전 마진을 만든 것에 가깝다.
하지만 코드 베이스가 계속 자라는 한, 같은 종류의 문제는 다른 형태로 반드시 다시 찾아온다.
원인 분석을 바탕으로 우선순위를 단기·중기·장기로 정리해봤다.

### 단기 — 인프라 레벨에서 즉시 가능한 조치

- **gp2 → gp3 EBS 변환** — 가장 즉각적이고 확실한 개선이다. gp3는 항상 3,000 IOPS를 보장하므로 버스트 크레딧이 소진되어 100 IOPS로 떨어지는 시나리오 자체가 사라진다. 무중단 전환이 가능하고 비용도 동일하거나 소폭 절감된다. EBS I/O 포화가 D-state thrashing의 직접 트리거였던 만큼, 이 한 줄로 문제 시나리오의 절반이 사실상 무력화된다.
- **`vm.swappiness` 운영 정책 점검** — 현재 10으로 설정했지만, 워크로드가 변하면 적정값도 달라진다. 빌드 시점·서비스 응답 시점의 swap 사용 패턴을 주기적으로 점검할 필요가 있다.

### 중기 — 빌드 메모리 자체를 줄이거나 가시화

- **`schema.ts` 도메인별 분할 검토** — OpenAPI 자동 생성 파일이 단일 44K 라인으로 유지되는 한, TypeScript 컴파일러는 매번 이 파일의 AST 전체를 메모리에 올린다. `auth`, `membership`, `study` 등 도메인 기준으로 나누면 각 컴포넌트가 필요한 타입만 임포트하게 되고, 타입 추론 메모리도 함께 줄일 수 있다. 다만 자동 생성 파이프라인 자체를 손봐야 하므로 비용이 작지 않다.
- **빌드 메모리를 측정 지표로 추가** — 현재 `scripts/build-benchmark.sh`로 빌드 시간을 측정하고 있는데, Node.js 피크 힙 사용량(`/usr/bin/time -v` 또는 `--max-old-space-size` 도달률)도 같은 보드에 올려두면 다음 임계점 접근을 조기에 감지할 수 있다. "왜 하필 v1.4.61"이라는 질문을 사후가 아니라 사전에 던지게 만드는 장치다.

### 장기 — 빌드 위치 자체를 옮긴다

- **GitHub Actions runner에서 빌드 + ECR push** — 빌드를 7GB RAM이 보장된 GitHub-hosted runner에서 수행하고, EC2는 이미지를 pull만 한다. EC2 메모리 한계라는 제약 자체가 사라지므로 동일한 종류의 문제가 다시 발생할 여지가 근본적으로 사라진다. ECR 비용이 추가되지만 미미한 수준이고, 배포 파이프라인을 EC2 의존에서 분리한다는 부수 효과도 크다.

정리하자면 단기적으로는 **gp3 변환으로 I/O 측 안전 마진을 확보**하고, 중기로는 **빌드 메모리 자체를 줄이고 측정 가능하게 만들고**, 장기적으로는 **빌드를 EC2 바깥으로 옮겨 제약을 우회**하는 방향이다.
각 단계는 서로 배타적이지 않으며, 단기 조치만으로도 당장의 위험은 크게 낮아진다.

## 마무리

이번 디버깅 과정에서 가장 크게 배운 점들을 정리하자면 다음과 같다.

- **SSH가 안 되면 단일 프로세스에 국한된 문제가 아니다.** 빌드 프로세스만 문제였다면 SSH는 살아있어야 한다. SSH까지 막혔다면 사용자 공간 프로세스 전반의 정지를 의심해야 한다.
- **OOM Kill과 D-state thrashing은 다르다.** OOM Kill은 커널 로그에 흔적이 남는다. D-state thrashing은 흔적이 거의 없다. "이유 없이 멈춤 + 재시작으로 해결" 패턴이라면 이 가능성을 의심해보자.
- **`buff/cache`는 비어있는 메모리가 아니다.** `free -m` 출력의 `buff/cache`가 크다고 여유가 있는 게 아니다. 커널이 페이지 캐시를 회수(reclaim)하려면 dirty 페이지의 write-back과 재접근 시의 재페치가 발생하고, EBS가 느리면 이 회수 과정 자체가 병목이 된다.
- **CloudWatch는 OS 내부 상태를 모른다.** AWS의 System Status Check는 가상화 레이어를 기준으로 동작하기 때문에, OS가 D-state로 막혀 있어도 "정상"으로 표시된다. 시스템 정지 의심 시에는 `VolumeQueueLength` 같은 EBS 지표를 함께 봐야 한다.
- **점진적 누적은 결국 임계점을 만든다.** v1.4.61 단일 릴리즈가 결정적이었던 게 아니라, 6버전 동안 동결돼 있던 `schema.ts`가 다시 자라기 시작하면서 누적된 결과였다. 임계점에 가까운 지표는 사후가 아니라 사전에 측정 가능하게 두는 게 안전하다.
- **가설은 실험으로 검증해야 한다.** CloudWatch 증거만으로도 충분할 수 있었지만, 직접 조건을 만들어 재현하고 swap 유무에 따른 차이를 비교했던 것이 결과적으로 가장 강력한 근거가 됐다.

다음에 비슷한 증상을 마주하더라도, 이번처럼 시간을 헤매지 않고 더 빨리 메모리·I/O 포화 가설을 떠올릴 수 있을 것 같다.
