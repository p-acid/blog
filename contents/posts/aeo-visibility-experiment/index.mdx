지금 다니는 회사는 중장년을 위한 온라인 강의·모임 서비스를 운영한다. ChatGPT에 이 서비스에 대해 물어보면 몇 년 전 언론 기사를 근거로 옛날 소개 문구를 그대로 읊었다.
서비스는 그 사이 많이 바뀌었고 후기도 1만 7천 건 넘게 쌓였는데, AI는 서비스 페이지가 아니라 오래된 기사를 들고 왔다.

기획에서 나온 첫 해법은 후기와 Q&A를 모은 **새 페이지를 만들자**는 것이었다. 그럴듯했지만 손을 대기 전에 한 가지가 궁금했다.

> 지금 있는 페이지는 AI 크롤러에게 어떻게 보이고 있을까?

이 글은 그 질문에서 시작해 7월 말부터 9월 말까지 두 달 동안 진행한 AEO(Answer Engine Optimization) 실험의 기록이다.
결론부터 말하면 **노출까지는 효과가 있었고, 유입으로는 이어지지 않았다.** 성공담보다는 실험을 어떻게 설계했고 어디서 틀렸는지를 남기는 쪽에 가깝다.

## 크롤러의 눈으로 사이트를 다시 보다

새 페이지를 기획하기 전에 코드베이스를 전수 조사했다. 크롤러가 콘텐츠를 발견하고, 읽고, 이해하는 단계별로 나눠 보니 결과는 생각보다 심각했다.

| 단계 | 있어야 하는 것 | 실제 상태 |
| --- | --- | --- |
| 발견 | sitemap에 공개 URL 전체 | 섹션 진입 URL 4개만 하드코딩 |
| 접근 | robots.txt 크롤러 허용 | AI 크롤러 13종 허용, llms.txt 있음 |
| 본문 읽기 | 초기 HTML에 콘텐츠 포함 | 상세 본문 전부 클라이언트 fetch, 크롤러에게는 로딩 스피너만 노출 |
| 이해 | 구조화 데이터(JSON-LD) | 코드베이스 전체에 0개 |
| 정규화 | canonical URL | 없음 |
| 신호 보존 | 영구 리다이렉트 | 레거시 → 새 경로 리다이렉트가 전부 307(임시) |

제대로 갖춰진 건 robots.txt 하나뿐이었다.
AI가 옛 기사를 인용하는 건 자사 페이지가 없어서가 아니라, **있는 페이지가 크롤러 입장에서는 존재하지 않는 상태**였기 때문이다.

### 새 메뉴보다 지도 등록이 먼저

팀에 설명할 때는 이런 비유를 썼다.

우리는 단골 많은 맛집인데 지도 앱에 제대로 등록돼 있지 않다. 그래서 손님이 "근처 괜찮은 곳"을 검색하면 택시 기사님의 오래된 기억이 대신 안내한다.
이때 필요한 건 메뉴를 하나 더 개발하는 일이 아니라, 있는 가게를 지도에 정확히 등록하는 일이다.

![모르는데 어떻게 가요](dont-know-how-to-go.jpg)

실험 설계 관점에서도 기존 페이지를 고치는 쪽이 훨씬 유리했다.

- **새 페이지**는 베이스라인이 없고 URL이 하나뿐이라 비교할 대상이 없다.
- **기존 상세 페이지**는 이미 검색 이력이 있어 전후 비교가 가능하고 수천 개라서 일부에만 먼저 적용하면 대조군을 만들 수 있다.

그래서 새 페이지는 보류하고 기존 페이지의 크롤 가능성을 고치는 실험으로 방향을 바꿨다. 새 페이지는 버린 게 아니라, 이 실험이 "기존 페이지로는 못 잡는 질문"을 특정해 주면 그때 만들 다음 단계로 남겨 뒀다.

## 실험 설계와 계측

### 네 가지의 가설

"AEO를 강화하면 매출이 오른다"는 하나의 가설로 두면, 실패했을 때 어디가 끊겼는지 알 수 없다. 그래서 사슬을 고리 단위로 나눠 각각 따로 판정하기로 했다.

| 가설 | 내용 | 주 지표 |
| --- | --- | --- |
| H1 크롤·색인 | 본문 SSR과 JSON-LD를 적용하면 크롤러가 실제 콘텐츠를 받고 색인이 실질화된다 | 봇 응답 크기, 검색 노출 |
| H2 인용 | 적용된 페이지가 AI 답변의 출처로 등장한다 | 고정 질문 20개에 대한 등장·인용 |
| H3 유입 | 적용 페이지의 검색·AI 유입이 대조군보다 늘어난다 | 주간 랜딩 세션 |
| H4 구매 | 이 경로의 유입이 구매로 이어진다 | first-touch 귀속 |

H1이 실패하면 H2~H4는 판정하지 않는다. 크롤러가 콘텐츠를 못 받는데 인용이나 유입을 따질 이유가 없기 때문이다.

H2에 쓸 질문 20개는 미리 정하고 실험이 끝날 때까지 바꾸지 않기로 했다. 서비스 이름을 넣어 묻는 브랜드 질문 4개와, 서비스를 모르는 사람이 관심사로 묻는 롱테일 질문 16개다.
롱테일은 타깃, 주제, 형식 세 축 중 몇 개가 들어가느냐로 구체성을 나눴다. 세 축이 다 들어간 질문은 서비스와 딱 맞는 질문이라, 여기서도 안 나온다면 콘텐츠가 아니라 가시성의 문제라고 볼 수 있다.

### 대조군은 id의 홀짝으로

적용군과 대조군을 나누는 방법으로 카테고리별 층화, 트래픽 기반 매칭 페어 같은 것들을 검토했다. 최종적으로는 가장 단순한 규칙을 골랐다.

```ts
const isTreatment = studyId % 2 === 0;
```

짝수 id는 적용군, 홀수 id는 대조군이다. 실측해 보니 두 그룹의 트래픽 균형이 매칭 페어 무작위보다 오히려 좋았고 새로 생기는 페이지도 별도 목록 관리 없이 자동으로 편입된다.
나중에 크롤 응답 크기의 before 값을 보니 두 그룹 차이가 7바이트였다. 배정이 잘 됐다는 사후 확인이었다.

### 전역 레버와 페이지 레버 구분 짓기

설계하다 보니 이번 변경이 성격이 다른 두 묶음이라는 게 보였다.

- **페이지 레버**: 상세 본문 SSR, Course·FAQPage JSON-LD. 적용군에만 배포할 수 있다.
- **전역 레버**: sitemap, canonical, Organization JSON-LD, 308 리다이렉트. 사이트 전체에 걸리니 대조군에도 들어간다.

대조군으로 인과를 주장할 수 있는 건 페이지 레버뿐이다. 전역 레버의 효과는 계절성이나 검색엔진 자체 변화와 분리할 수 없으니, "관찰됨" 정도로만 쓰고 "전역 레버가 X를 올렸다"는 결론은 쓰지 않기로 미리 정했다.
이 구분은 뒤에서 대조군 수치가 예상과 다르게 움직였을 때 실험을 지켜 준 장치가 됐다.

### 판정 규칙 정하고 지표 기록하기

결과를 보고 나서 기준을 고르면 무엇이든 성공으로 만들 수 있다. 그래서 임계값, 추정 방법, 관측 시점을 배포 전에 문서로 확정하고, 그 뒤로는 손대지 않기로 했다.

- **H1**: 적용군 페이지 20개 모두 배포 검증 통과, AI 봇 200 응답의 gzip 크기 중앙값 18,000B 이상
- **H2**: 롱테일 질문에서 2개 이상 등장, 자사 상세 URL 인용 1건 이상
- **H3**: 음이항 DiD, 유의수준 0.05, 표본이 부족한 채널은 검정하지 않고 서술만
- **H4**: 표본상 유의성이 나올 수 없어 참·거짓 판정 대상에서 제외

H4를 미리 뺀 건 계산해 본 결과다. AI 경유 유입이 28일에 25명 수준이라 12주를 모아도 구매는 한 자릿수에 그친다. 유의성이 나올 수 없는 지표를 성공 기준에 넣으면 나중에 해석만 꼬인다. 그래서 H4는 "귀속 계측이 실제로 작동하는가"만 확인하기로 했다.

기준값을 모으는 데서 첫 번째 실수가 나왔다.

ALB 액세스 로그를 Athena로 집계했더니 결과가 "3주간 AI 봇 크롤 3회"였다. AI가 아예 오지 않으니 인용도 안 되는구나 싶었다.
그런데 Googlebot도 46회밖에 안 잡혀 이상해서 확인해 보니, 테이블 정규식이 실제 ALB 로그 포맷과 맞지 않아 **전체 로그 중 2.5%만 파싱**되고 있었다.
Athena의 RegexSerDe는 매칭에 실패한 행을 버리지 않고 모든 컬럼을 NULL로 돌려준다. 에러 없이 조용히 과소집계가 되는 것이다.

```sql
-- 파싱률 검증. WHERE 조건을 걸면 NULL 행이 빠져서 검증이 무력화된다
SELECT count(*) AS total, count(request_url) AS parsed
FROM alb_logs;
```

정규식을 고쳐 다시 집계하니 숫자가 완전히 달라졌다.

| 크롤러 | 처음 집계 | 정정 후 (3주) |
| --- | ---: | ---: |
| Googlebot | 46 | 104,317 |
| AI 봇 합계 | 3 | 14,294 |
| 네이버 Yeti | 0 | 36,498 |

AI 봇은 이미 상세 페이지를 3주에 3,709번 요청하고 있었다. 사용자 질문에 반응해 실시간으로 페이지를 가져가는 ChatGPT-User만 4,800회였다.

이 발견으로 H1을 다시 정의했다. 문제는 크롤 **횟수**가 아니라 크롤할 때 **받아 가는 내용**이었다. 봇은 3,709번 찾아와서 3,709번 로딩 스피너만 받아 갔다.
그래서 주 지표를 "AI 봇 크롤 수"에서 "AI 봇이 받는 200 응답의 크기"로 바꿨다. 수요는 이미 충분한데 공급이 비어 있었으니, 오히려 개입의 근거가 강해진 셈이다.
그 뒤로는 어떤 집계든 파싱률부터 확인하는 걸 규칙으로 삼았다.

## 구현하며 만난 함정들

적용군에는 후기, Q&A, 커리큘럼, 가격, 진행자 정보를 서버에서 렌더하고 `Course`, `BreadcrumbList`, `FAQPage` JSON-LD를 붙였다. 구현 자체는 어렵지 않았다.
까다로웠던 건 **사람이 보는 화면에는 아무 문제가 없는데 크롤러와 측정에서만 깨지는 것들**이었다.

### 검증 스크립트의 오판을 바로잡다

배포 직후 봇 User-Agent로 적용군과 대조군 페이지를 20개씩 요청해 검증했는데, 대조군에서도 JSON-LD가 20/20으로 나왔다. 대조군이 오염된 줄 알고 식은땀이 났다.

원인은 스크립트가 `application/ld+json` 태그의 **존재 여부**만 봤다는 것이다. 같은 릴리스에 전역 레버인 Organization JSON-LD가 함께 나가면서 모든 페이지가 그 조건을 만족하게 됐다.
타입 단위로 다시 보니 적용군은 `Organization, Course, BreadcrumbList`, 대조군은 `Organization`뿐이었다. 배포는 정확했고 판정 도구가 틀렸다.

### notFound()가 200을 내는 이유를 찾다

존재하지 않는 상세 페이지 id가 HTTP 200을 돌려주는 soft 404 상태여서, 백엔드가 404를 주면 `generateMetadata`에서 `notFound()`를 부르도록 고쳤다. 그런데 배포 후에도 Googlebot은 200을 받았다.
응답 본문에는 404 폴백이 분명히 들어 있었다.

```text
"digest":"NEXT_HTTP_ERROR_FALLBACK;404"
```

Next.js가 404 폴백을 **스트리밍으로 밀어 넣고** 있었고 그 시점에는 이미 200 헤더가 나간 뒤였다. 루트 레이아웃이 앱 전체를 Suspense로 감싸고 있었기 때문이다.

```tsx
<Suspense fallback={<LoadingSpinnerScreen />}>
  <Providers>{children}</Providers>
</Suspense>
```

로컬 프로덕션 빌드로 `notFound()` 호출 위치별로 실험해 보니 원인이 두 겹이었다.

| 경로 | `notFound()` 위치 | 현재 | Suspense 제거 후 |
| --- | --- | ---: | ---: |
| 없는 라우트 | 라우팅 단계 | 404 | 404 |
| 프로필 상세 | Page 컴포넌트 | 200 | 404 |
| 강의 상세 | generateMetadata | 200 | 200 |

루트 Suspense가 Page 단계의 `notFound()`를 무력화하고 있었고 `generateMetadata`의 `notFound()`는 Suspense를 없애도 200이었다. 메타데이터가 셸 이후에 해소되기 때문이다.
앱 전체의 `notFound()`가 걸린 문제라 실험에서 떼어 별도 과제로 넘겼다. sitemap에는 실제로 존재하는 id만 들어가니 판정에는 영향이 없다고 봤다.

이 문제는 10월에 정리됐다. 루트 레이아웃에서 User-Agent를 보고 **로봇에게만 Suspense 경계 없이 렌더**하도록 바꿨다.

```tsx
const isHtmlLimitedBot = !!userAgent && HTML_LIMITED_BOTS_RE.test(userAgent);
```

브라우저는 경계를 그대로 유지한다. 경계를 걷어내면 전 페이지 TTFB가 320ms 늘었기 때문이다. 사람에게는 스트리밍으로 빠른 첫 화면을, 로봇에게는 상태 코드까지 확정된 완성본을 주는 구조다.

### head 밖으로 나간 canonical을 되돌리다

실험 중에 커뮤니티 글 하나가 옛 주소와 새 주소로 따로 색인돼 검색 클릭이 나뉘는 현상이 보였다. Search Console은 이 글을 "사용자 선언 표준 URL: 없음"으로 잡고 있었다.
canonical 값은 정상이었고 문제는 **위치**였다. Googlebot이 받은 HTML에서 `<link rel="canonical">`이 `</head>` 뒤에 있었다.

Next.js 15.2부터는 메타데이터도 스트리밍되고 `htmlLimitedBots`에 해당하는 UA에게만 메타데이터를 head 안에 블로킹으로 넣어 준다. 그런데 기본 목록의 Google 패턴은 이렇다.

```text
[\w-]+-Google|Google-[\w-]+
```

`Google-InspectionTool`은 잡지만 정작 색인 크롤러인 `Googlebot`은 잡지 못한다. 10월에 다시 측정해 보니 AI 답변 엔진 봇들도 목록에 없어서 title, canonical, og 태그가 본문 쪽으로 흘러나가고 있었다. AEO 실험을 하면서 정작 AI 봇에게 메타데이터를 head 밖으로 주고 있었던 셈이다.

목록에 봇들을 더하면서 함정이 하나 더 있었다. `htmlLimitedBots`는 기본 목록에 **추가되는 게 아니라 통째로 대체**한다. 그대로 덮어쓰면 카카오톡 미리보기와 네이버 크롤러가 회귀한다. 그래서 기본 목록을 import해 이어 붙였다.

```ts
import { HTML_LIMITED_BOT_UA_RE_STRING } from "next/dist/shared/lib/router/utils/is-bot";

export const HTML_LIMITED_BOTS_RE = new RegExp(
  ["Googlebot", "GPTBot", "OAI-SearchBot", "ChatGPT-User", "ClaudeBot", /* ... */ HTML_LIMITED_BOT_UA_RE_STRING].join("|"),
  "i",
);
```

이 정규식 하나를 `next.config`의 `htmlLimitedBots`와 위의 Suspense 분기가 함께 쓴다. 둘이 어긋나면 메타데이터는 head에 들어갔는데 404는 못 붙는 UA가 생기기 때문이다.

### Safari가 자른 쿠키를 서버로 옮기다

H4를 측정하려면 사용자가 처음 어디서 들어왔는지(first-touch)를 가입이나 구매 시점까지 기억해야 한다. 처음에는 클라이언트에서 `document.cookie`로 400일짜리 쿠키를 심었다.
그런데 Safari의 ITP는 **스크립트로 심은 쿠키의 수명을 7일로 강제로 줄인다.** 검색으로 들어와 8일 뒤에 가입하면 유입 출처가 사라진다.

서버 응답의 `Set-Cookie`는 이 제한을 받지 않아서, 쿠키를 심는 위치를 미들웨어로 옮겼다. 옮기면서 `cookies.set()`이 값을 이미 인코딩해 준다는 걸 몰라 이중 인코딩(`%257B`)으로 파싱이 깨지기도 했고 프록시 뒤에서 `nextUrl.origin`이 내부 호스트로 잡혀 사이트 안 이동을 외부 유입으로 오판하기도 했다.

배포 2주 뒤 BigQuery에서 브라우저별로 7일 넘게 유지된 쿠키 비율을 봤다. 절단이 살아 있다면 Safari만 0에 가까워야 하는데, Safari가 20.5%로 Chrome(17.0%)보다 오히려 높았다. 설정한 뒤에도 실제 데이터로 한 번 더 확인하고 나서야 H4 계측을 확정했다.

## 운영하면서 바꿔야 했던 규칙들

판정 규칙을 미리 못 박아 뒀지만 돌려 보니 지킬 수 없는 조건이 나왔다. 관측이 시작된 뒤 규칙을 바꾸면 사전 등록의 의미가 약해지니, 바꿀 때마다 이유와 시점을 문서에 남기고 그 변경이 결과에 유리하게 작용하는지 따로 확인했다.

**대조군도 25% 커졌다.** H1 규칙에는 "대조군 응답 크기는 before 대비 ±10% 이내"라는 조건이 있었는데, canonical과 Organization JSON-LD가 대조군에도 붙으면서 25% 커졌다. 전역 레버와 페이지 레버를 나눠 둔 덕분에 실험을 버리지 않고 규칙만 차분 판정으로 고칠 수 있었다.

```text
적용군 순증 = (적용 after - before) - (대조 after - before)
```

**자동 수집이 막힌 엔진은 뺐다.** H2는 AI 엔진 세 곳에 같은 질문 20개를 3번씩 물어 "3번 중 2번 등장"을 기준으로 삼았다. 그런데 Perplexity는 Cloudflare가 브라우저 지문 단위로 자동화를 막았고 손으로 모으기에는 시간이 부족했다. before가 없는 엔진을 억지로 넣는 것보다 빼는 게 정직하다고 판단해 ChatGPT와 Gemini 두 엔진으로 줄이고 임계값도 비례해 낮췄다.

**배포일이 당겨져 before 창이 5일이 됐다.** Search Console은 등록 전 기간의 데이터를 소급해서 주지 않아, 등록 후 2주를 기다려 배포한다는 조건을 걸어 뒀다. 실제 배포는 5일 만에 나갔다. Search Console 지표는 보조로 내리고, 주 단위 시계열은 8주 이력이 있는 GA4로 봤다.

## 결과

### H1 크롤·색인, 합격

배포 4주 뒤, ALB 로그로 AI 봇 6종의 200 응답 크기(gzip 중앙값)를 집계했다. 이번에는 파싱률부터 확인했다(99.97%).

| 그룹 | before | after |
| --- | ---: | ---: |
| 적용군 | 10,346B | **40,673B** |
| 대조군 | 10,339B | 13,634B |

적용군은 임계값의 2.26배로 합격했고 차분으로 본 순증도 약 27KB였다.
크롤 횟수는 두 그룹 모두 하루 50회 남짓에서 77회 정도로 똑같이 늘었다. sitemap 제출 같은 전역 요인 때문이다. 처음 계획대로 크롤 횟수를 주 지표로 뒀다면 이걸 효과로 착각했을 것이다.

검색 노출도 적용군 쪽으로 기울었다. 사전에 정한 5일 창에서 적용군 노출은 85% 늘었고 대조군은 3% 늘었다.
다만 before 창이 짧아 추세를 보정하지 못한 수치라, 다른 창으로 보면 비율이 1.2배에서 1.8배까지 흔들렸다. 그래서 크기가 아니라 **"적용군이 앞선다"는 방향**만 근거로 삼았다.

### H2 인용, 확인은 나아지고 발견은 아직

배포 6주와 9주 뒤에 같은 질문을 다시 물었다.

| 지표 | before | 1회차 | 2회차 |
| --- | ---: | ---: | ---: |
| 롱테일 12문항 중 등장 문항 | 0 | 0 | 0 |
| 자사 상세 URL 인용 | 0건 | 6건 | 16건 |
| 브랜드 오인(다른 회사로 착각) | 있음 | 있음 | 없음 |

서비스 이름을 넣어 묻는 브랜드 질문에서는 확실히 나아졌다. ChatGPT가 서비스의 정책 페이지를 근거로 가격 구조를 정확히 설명했고 해외의 비슷한 이름을 가진 서비스로 착각하는 일도 사라졌다.
인용된 상세 URL 8개가 **전부 짝수 id, 즉 적용군**이었다는 점도 눈에 띄었다. H2는 브랜드 단위 지표라 판정에는 쓰지 않았지만 기억에 남는 장면이었다.

반면 서비스를 모르는 사람이 관심사로 묻는 롱테일 질문에서는 성공선에 닿지 못했다. 언급이 조금씩 생기긴 했지만 매번 다른 질문에서 한 번씩 나와, 어느 질문도 "3번 중 2번"에 닿지 않았다.
Gemini는 출처 없이 모델 자체의 기억으로 답하는 비중이 늘면서 가격을 회차마다 다르게 지어내기도 했다. 페이지를 고치는 것만으로 모델이 이미 기억하는 내용까지 바로잡을 수는 없었다.

### H3 유입, 효과 없음

배포 6~8주 뒤 GA4 랜딩 세션으로 DiD를 돌렸다.

| 구분 | 적용/대조 비율 (전) | 적용/대조 비율 (후) |
| --- | ---: | ---: |
| 자연 검색 전체 | 0.808 | 0.818 |

비율이 그대로였다. 표본이 충분해서 검출력 조건은 넉넉히 통과했으니 "판정 불가"가 아니라 **"1.3배 이상의 유입 효과는 없다"**로 읽었다. AI 경유 유입은 표본이 너무 작아 서술로만 남겼다.

## 정리

H1과 H3를 나란히 놓으면 이렇다. **크롤러가 콘텐츠를 받고 노출이 늘어나는 단계까지는 효과가 있었지만 클릭으로는 이어지지 않았다.**
늘어난 노출이 원래 클릭이 적은 롱테일 쿼리였을 수도 있고 순위나 스니펫이 클릭을 부를 만큼 바뀌지 않았을 수도 있다. 사전에 정한 판정 경로에 따라, 기존 페이지로 잡지 못하는 쿼리를 특정해 새 페이지를 기획하는 다음 단계로 넘어갔다.
9월 말에는 대조군을 해제해 홀수 id 페이지에도 같은 개선을 적용했다.

두 달 동안 가장 크게 남은 건 결과보다 과정이었다.

- **지표는 개입이 실제로 바꾸는 것에 맞춰야 한다.** 크롤 수를 지표로 뒀다면 효과가 없다고 결론 냈거나, 전역 요인을 효과로 착각했을 것이다.
- **집계 도구부터 의심해야 한다.** 파싱률 2.5%짜리 베이스라인으로 방향을 정할 뻔했고 검증 스크립트는 정상 배포를 불합격시켰다.
- **사람에게 맞춘 기본값은 로봇과 측정에 불리할 수 있다.** 스트리밍과 클라이언트 쿠키는 사람에게는 문제가 없었지만 상태 코드와 메타데이터, 유입 기록을 망가뜨렸다.
- **실패한 가설도 그대로 보고해야 다음 판단이 쉬워진다.** 유입 효과가 없었다는 결과 덕분에 "새 페이지를 만들까"라는 처음 질문에 이번에는 근거를 가지고 답할 수 있게 됐다.

처음 기획대로 새 페이지부터 만들었다면 비교할 대상도 없이 "효과가 있는 것 같다"는 말만 남았을 것이다.
지도 등록을 먼저 해 본 덕분에 어디까지가 등록으로 되는 일이고, 어디부터가 새 메뉴가 필요한 일인지 선을 그을 수 있었다.
